# Data dictionary

| Table | Key fields | Purpose and integrity rule |
|---|---|---|
| `users` | `id`, `email`, `password_hash` | User identity; email is unique and only password hashes are stored. |
| `roles` | `id`, `name` | Allowed roles: `RESEARCHER`, `ADMIN`. |
| `user_roles` | `user_id`, `role_id` | Many-to-many assignment with composite primary key. |
| `vulnerability_reports` | `id`, `reporter_id`, `status`, `severity` | Authoritative report; title and description cannot be blank. |
| `report_status_history` | `report_id`, `from_status`, `to_status` | Trigger-generated lifecycle history; no application edit/delete endpoint. |
| `patches` | `report_id`, `reference` | Remediation history; one reference cannot repeat for a report. |
| `bounty_payouts` | `report_id`, `amount`, `reference` | Ledger; one payout per report, positive amount, unique reference. |
| `audit_logs` | `actor_id`, `action`, `entity_id` | Auditable record of sensitive actions. |

Status-history rows are generated by database triggers, but the schema does not
install a guard against direct UPDATE/DELETE on that table. The append-only database
guard applies to `audit_logs`; payout records and reviewed patches have their own
write guards.

## MongoDB evidence document

`report_evidence` has `_id`, `reportId`, `submittedByUserId`, `reproduction`, `affectedComponents`, `technicalMetadata`, `sanitizedPocNotes`, `createdAt`, and `updatedAt`. It holds flexible, sanitized evidence. Submitted content must exclude credentials and executable exploit payloads.

## Reviewed patches and payout eligibility

Patches now carry `review_status` (PENDING/APPROVED/REJECTED), nullable legacy
`submitted_by_id`, `reviewed_by_id`, `reviewed_at`, and `review_note`. New submissions
require an actor and remediation status; rejected reviews require a note. Reviewed
patches are retained and immutable. Approval permits PATCHED, followed by CLOSED.
Payouts are immutable records for CLOSED reports with an approved patch; INR/USD
are supported. The recipient is always the report's researcher. Existing patches
migrate to PENDING; existing payouts remain untouched. Legacy completed reports
without approved patches are historical records, not newly payout-eligible.

Report, patch, and payout triggers append audit events in the same SQL transaction.
Audit rows reject UPDATE/DELETE. Database owners can bypass triggers, so these
controls demonstrate application integrity rather than tamper-proof storage.
